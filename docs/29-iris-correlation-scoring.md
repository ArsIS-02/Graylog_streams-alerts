# Глава 29. IRIS: корреляция и скоринг алертов в TicketBridge

Каждое событие Graylog раньше становилось отдельным алертом IRIS: однотипные срабатывания (подбор пароля SSH каждые 5 минут) генерировали десятки алертов по одному хосту. Внедряем модель SOAR Security Vision: дедупликация по связке «правило + актив», накопительный скоринг и автоэскалация в кейс.

## Модель

- **Ключ корреляции**: `event_definition_id` правила Graylog + главный актив (первый не-учётный актив из обогащения HostDeck; если только учётки — первая учётка; иначе хост-источник события).
- **Дедупликация**: повторное срабатывание той же связки в пределах окна не создаёт новый алерт, а добавляет комментарий-обогащение в таймлайн открытого: номер срабатывания, время, вклад в скор, новые активы/IoC, ссылка на Replay Search.
- **Скоринг**: веса по приоритету Graylog — high 50 / medium 20 / low 5; MITRE-техника (T#### в тексте или тегах) — множитель ×2.
- **Эскалация**: скор ≥ 100 за окно 24 ч → алерт эскалируется в кейс IRIS (`POST /api/v2/alerts/escalate/{id}`): статус алерта → Escalated, создаётся case «[Корреляция] \<правило\> — \<актив\>».
- **Продолжение кейса**: после эскалации один активный кейс остаётся привязанным к связке «правило + актив» даже после окна скоринга. Повторы создают события в таймлайне кейса, накапливают скор и обновляют доказательства; новый алерт/кейс не создаётся.
- **Закрытие и подавление**: после закрытия кейса маловесные повторы подавляются на 24 ч. Событие весом ≥ 50 переоткрывает тот же кейс; после истечения подавления начинается новый жизненный цикл.
- **Безопасный сбой**: если состояние существующего кейса неизвестно, его `case_id` сохраняется и новый алерт не создаётся. Исходное событие остаётся в Graylog.

## Реализация

Всё в `app.py` TicketBridge (сервис `ticketbridge.service` на redos-server):

```sql
CREATE TABLE IF NOT EXISTS iris_corr(
    corr_key TEXT PRIMARY KEY,          -- правило|актив
    alert_id INTEGER NOT NULL,
    score REAL NOT NULL DEFAULT 0,      -- накопленный скор
    hit_count INTEGER NOT NULL DEFAULT 1,
    first_ts REAL, last_ts REAL,
    escalated INTEGER NOT NULL DEFAULT 0,
    case_id INTEGER,
    case_closed_ts REAL,                -- начало подавления после закрытия кейса
    last_evidence_ts REAL);             -- ограничение частоты новых ZIP
```

Существующая база мигрируется автоматически через `PRAGMA table_info` и `ALTER TABLE`, без удаления
строк и потери `case_id`.

Ключевые функции:

- `iris_corr_key(event, assets)` — ключ «правило + главный актив»;
- `rule_weight(event)` — вес по приоритету + MITRE-множитель;
- `_correlated_send(event, payload, assets, iocs)` — весь жизненный цикл связки;
- `_iris_enrich(...)` — комментарий-обогащение исходного алерта;
- `_iris_add_case_event(...)` — событие в таймлайне существующего кейса;
- `_escalate_correlated(...)` — эскалация в кейс при достижении порога;
- `_iris_case_state(...)` и `POST /api/v2/cases/{id}/reopen` — состояние и контролируемое переоткрытие.

Статусы алертов, считающиеся «живыми» для обогащения: Unspecified(1), New(2), Assigned(3),
In progress(4), Pending(5), Escalated(8). Для уже эскалированной связки решающим является состояние
самого кейса: закрытый исходный алерт не мешает продолжать открытый кейс.

Zabbix-события идут отдельным путём (`iris_dedup`: один `zabbix_event_id` = один алерт) и в корреляцию не попадают.

## Настройки (env)

| Переменная | Умолчание | Смысл |
|---|---|---|
| `TB_IRIS_CORR` | `1` | вкл/выкл корреляцию (`0` — старое поведение) |
| `TB_SCORE_WINDOW` | `86400` | окно корреляции и скоринга, сек |
| `TB_SCORE_THRESHOLD` | `100` | порог автоэскалации в кейс |
| `TB_SCORE_HIGH` / `TB_SCORE_MEDIUM` / `TB_SCORE_LOW` | `50` / `20` / `5` | веса по приоритету Graylog |
| `TB_SCORE_MITRE_MULT` | `2` | множитель за MITRE-технику |
| `TB_CASE_SUPPRESSION` | `86400` | подавление маловесных повторов после закрытия кейса, сек |
| `TB_CASE_REOPEN_MIN_WEIGHT` | `50` | минимальный вес одиночного события для переоткрытия |
| `TB_CASE_EVIDENCE_INTERVAL` | `3600` | минимальный интервал между новыми evidence ZIP активного кейса, сек |
| `TB_RULE_WEIGHTS` | `{}` | JSON-карта точечных весов: ключ — id правила или префикс заголовка, значение — вес, заменяющий приоритетный |

## Точечные веса правил (матрица рисков)

Помимо приоритетов действует таблица `TB_RULE_WEIGHTS` (JSON одной строкой в `ticketbridge.env`): ключ — точный `event_definition_id` или префикс заголовка правила; при совпадении нескольких префиксов берётся самый длинный; MITRE-множитель применяется поверх.

Тиры (порог эскалации 100):

- **100** — TRAFFICLENS - Компрометация (одно срабатывание = кейс)
- **90** — Windows - DCSync; LNX/macOS - Обратная оболочка; macOS - Выгрузка паролей из Keychain
- **80** — CANARY; COWRIE; SANDBOX; TRAFFICLENS (IOC, обращение, ретропроверка); Kerberoasting (Windows, FREEIPA)
- **70** — PowerShell download&execute; Defender обнаружил; подбор + успешный вход; WAZUH критичный (12+)
- **60** — LOGATLAS high; брутфорсы (LNX SSH, FREEIPA, HOSTDECK, HOMEREPO); переподпись репозитория
- **40–50** — KEENETIC вход/отказ в админку; HOSTDECK проверка fail
- **20–30** — блокировки и сканирование KEENETIC; потеря связи с KDC; консоль root; WAZUH важный (9–11)
- **2–10** — тишина источников, сохранение конфигурации, PPPoE, новые устройства, деградации, предупреждения
- **1** — дайджесты, отчёты, штатные sudo, «агент вернулся»

Правила вне таблицы — по приоритету (50/20/5). Изменение веса: правка JSON в `ticketbridge.env` + `systemctl --user restart ticketbridge`; контроль — `custom_weights` в `/correlation/status`.

### Разбор первых суток (17.11)

За первые ~21 ч после внедрения: 271 событие Graylog (265 с флагом alert) → **56 алертов IRIS** (на IRIS-пути: 155 срабатываний → 54 новых алерта + 101 обогащение; снижение потока ~65%) и **20 автоэскалаций** в кейсы (кейсы #3–#22).

**Найденная ошибка**: ключи-префиксы заголовков фактически не работали — в payload вебхука Graylog нет поля `event_definition_title`, поэтому совпадение возможно только по точному `event_definition_id`. Все 53 записи матрицы переписаны на id правил (53 префикса → 74 правила; контроль: `custom_weights: 74` в `/correlation/status`).

Корректировки весов по итогам суток (штатная активность давала кейсы):

| Правило | Было | Стало | Причина |
|---|---|---|---|
| macOS - Обратная оболочка (/dev/tcp, pty.spawn) | 90 | 40 | Ложные срабатывания на командных строках агентов мониторинга и админа (паттерны встречаются в текстах поисковых запросов и heredoc); 3 кейса за сутки. Одиночный FP больше не эскалирует, 2+ хита за сутки — кейс. |
| KEENETIC - Вход в админку роутера (SSH) | 40 | 5 | Штатные входы админа со своего хоста (9+ за сутки → скор 900, кейс). Эскалация теперь при 10+ входах/сутки. |
| KEENETIC - Отказ во входе на роутер | 40 | 8 | Внутренние отказы (скрипты/сохранённые учётки), 6+/сутки → кейс. Эскалация при 7+ отказах/сутки. |
| AUDIT - Работа с модулями ядра | — (50) | 10 | 23 соб/сутки, 5 кейсов на 4 хостах: штатные загрузки модулей (контейнерный рантайм, сервисы). |
| AUDIT - Изменение systemd-юнитов | — (20) | 10 | Штатные обновления пакетов/деплой; кейс при 6 хитах. |
| Контейнеры: всплеск ошибок | — (20) | 8 | 58 соб/сутки (loki, grafana, wazuh.manager), 3 кейса. |
| macOS - Подключено мобильное устройство (не Apple) | — (50×2) | 10 | Подключение телефона к MacMini → мгновенный кейс (50 × MITRE 2 = 100). |
| macOS - Сканеры сети (nmap, masscan, arp-scan) | — (20×2) | 8 | Админский nmap с MacMiniM2, 32 соб/сутки. |

Первоначальная модель после эскалации и закрытия алерта могла создать новый алерт и повторный кейс
(например, #11, #17 и #22 для macOS reverse shell). Вечером 17.11 это поведение заменено продолжением
активного кейса, подавлением после закрытия и контролируемым reopen. Понижение веса повторяющихся FP
по-прежнему необходимо: оно уменьшает ложную эскалацию и нежелательное переоткрытие.

## Наблюдаемость

- `GET /correlation/status?key=$TB_KEY` — текущие связки, `case_id`, время обнаружения закрытия и последнего evidence ZIP; также показывает все три новых параметра.
- GELF: `iris_enriched`, `iris_escalated`, `iris_case_enriched`, `iris_case_suppressed`, `iris_case_reopened`.
- Ошибки: `iris_enrich_error`, `iris_escalate_error`, `iris_case_event_error`, `iris_case_state_error`, `iris_case_reopen_error`.
- Sweeper удаляет старые записи без кейса и записи закрытых кейсов после окончания подавления; активные кейсы не удаляются по возрасту.

## Проверка в бою

Пять одинаковых событий medium (вес 20) по одному активу за 6 секунд:

- создан **один** алерт IRIS (а не пять);
- четыре комментария-обогащения (№2…№5, скор 40 → 60 → 80 → 100);
- на пятом срабатывании скор достиг порога → алерт автоматически эскалирован в кейс, статус → Escalated.

Проверка MITRE-множителя: medium + T1078 → вес 40; два срабатывания → скор 80, эскалации нет — порог не достигнут.

## Тюнинг

- Правило эскалируется слишком рано → понизить его приоритет в Graylog (вес) или поднять `TB_SCORE_THRESHOLD`.
- Полный откат: `TB_IRIS_CORR=0` в `ticketbridge.env` + `systemctl --user restart ticketbridge`.
- Выборочного исключения отдельных правил из корреляции пока нет — кандидат на доработку (список `TB_CORR_EXCLUDE`).
