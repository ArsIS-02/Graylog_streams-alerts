# Глава 29. IRIS: корреляция и скоринг алертов в TicketBridge

Каждое событие Graylog раньше становилось отдельным алертом IRIS: однотипные срабатывания (подбор пароля SSH каждые 5 минут) генерировали десятки алертов по одному хосту. Внедряем модель SOAR Security Vision: дедупликация по связке «правило + актив», накопительный скоринг и автоэскалация в кейс.

## Модель

- **Ключ корреляции**: `event_definition_id` правила Graylog + главный актив (первый не-учётный актив из обогащения HostDeck; если только учётки — первая учётка; иначе хост-источник события).
- **Дедупликация**: повторное срабатывание той же связки в пределах окна не создаёт новый алерт, а добавляет комментарий-обогащение в таймлайн открытого: номер срабатывания, время, вклад в скор, новые активы/IoC, ссылка на Replay Search.
- **Скоринг**: веса по приоритету Graylog — high 50 / medium 20 / low 5; MITRE-техника (T#### в тексте или тегах) — множитель ×2.
- **Эскалация**: скор ≥ 100 за окно 24 ч → алерт эскалируется в кейс IRIS (`POST /api/v2/alerts/escalate/{id}`): статус алерта → Escalated, создаётся case «[Корреляция] \<правило\> — \<актив\>».
- **Самолечение**: если алерт закрыт вручную, а события продолжаются — TicketBridge замечает это по статусу (GET алерта) и заводит новый алерт, заменяя запись.

## Реализация

Всё в `app.py` TicketBridge (сервис `ticketbridge.service` на redos-server):

```sql
CREATE TABLE IF NOT EXISTS iris_corr(
    corr_key TEXT PRIMARY KEY,          -- правило|актив
    alert_id INTEGER NOT NULL,
    score REAL NOT NULL DEFAULT 0,      -- накопленный скор
    hit_count INTEGER NOT NULL DEFAULT 1,
    first_ts REAL, last_ts REAL,
    escalated INTEGER NOT NULL DEFAULT 0,
    case_id INTEGER);
```

Ключевые функции:

- `iris_corr_key(event, assets)` — ключ «правило + главный актив»;
- `rule_weight(event)` — вес по приоритету + MITRE-множитель;
- `_correlated_send(event, payload, assets, iocs)` — точка входа: ищет открытую связку в `iris_corr`, обогащает или создаёт алерт;
- `_iris_enrich(...)` — комментарий-обогащение в таймлайн;
- `_escalate_correlated(...)` — эскалация в кейс при достижении порога.

Статусы IRIS, считающиеся «живыми» для обогащения: Unspecified(1), New(2), Assigned(3), In progress(4), Pending(5), Escalated(8). Closed(6) и Merged(7) завершают связку — следующее событие создаст новый алерт.

Zabbix-события идут отдельным путём (`iris_dedup`: один `zabbix_event_id` = один алерт) и в корреляцию не попадают.

## Настройки (env)

| Переменная | Умолчание | Смысл |
|---|---|---|
| `TB_IRIS_CORR` | `1` | вкл/выкл корреляцию (`0` — старое поведение) |
| `TB_SCORE_WINDOW` | `86400` | окно корреляции и скоринга, сек |
| `TB_SCORE_THRESHOLD` | `100` | порог автоэскалации в кейс |
| `TB_SCORE_HIGH` / `TB_SCORE_MEDIUM` / `TB_SCORE_LOW` | `50` / `20` / `5` | веса по приоритету Graylog |
| `TB_SCORE_MITRE_MULT` | `2` | множитель за MITRE-технику |

## Наблюдаемость

- `GET /correlation/status?key=$TB_KEY` — текущие связки: ключ, alert_id, скор, счётчик, флаг эскалации, case_id.
- GELF-события в Graylog: `tb_event=iris_enriched` (обогащение), `iris_escalated` (эскалация в кейс), `iris_enrich_error` / `iris_escalate_error`.
- Фоновый sweeper чистит записи корреляции старше двух окон.

## Проверка в бою

Пять одинаковых событий medium (вес 20) по одному активу за 6 секунд:

- создан **один** алерт IRIS (а не пять);
- четыре комментария-обогащения (№2…№5, скор 40 → 60 → 80 → 100);
- на пятом срабатывании скор достиг порога → алерт автоматически эскалирован в кейс, статус → Escalated.

Проверка MITRE-множителя: medium + T1078 → вес 40; два срабатывания → скор 80, эскалации нет — порог не достигнут.

## Тюнинг

- Правило эскалируется слишком рано → понизить его приоритет в Graylog (вес) или поднять `TB_SCORE_THRESHOLD`.
- Полный откат: `TB_IRIS_CORR=0` в `ticketbridge.env` + `systemctl --user restart ticketbridge`.
- Выборочного исключения отдельных правил из корреляции пока нет — кандидат на доработку (список `TB_CORR_EXCLUDE`).
