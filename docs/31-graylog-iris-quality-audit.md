# Глава 31. Еженедельный аудит качества Graylog и итогов IRIS

## Назначение

Отдельный read-only контур на `redos-server` раз в неделю отвечает на четыре вопроса:

1. Совпадает ли действующая конфигурация Graylog с каталогом `main` на GitHub (`drift`).
2. Не стали ли активные Lucene-запросы слишком широкими (`fp-check` на недавнем корпусе сообщений).
3. Как администратор закрывал алерты IRIS за последние 7 суток: False Positive, Legitimate,
   подтверждённые срабатывания и записи без разрешения.
4. Какие сочетания правила, хоста, пользователя и команды повторяются среди закрытий
   False Positive/Legitimate и требуют ручного разбора как кандидаты на тюнинг.

Результат публикуется в HomeWiki: **«Graylog/IRIS - Еженедельный аудит качества правил»**,
страница `art-graylog-quality-weekly`. История остаётся на сервере. Почтовые уведомления не создаются.
Рекомендации не применяются автоматически: аудит не добавляет исключения и не ослабляет правила.

## Архитектура

- `/home/redos/graylog-quality/repo` — отдельный чистый clone `Graylog_streams-alerts`;
  старый `/home/redos/Graylog_streams-alerts` не используется.
- `/home/redos/graylog-quality/quality_audit.py` — оркестратор, установленный вне clone,
  поэтому `git pull --ff-only` не упирается в локальные untracked-файлы.
- `/home/redos/graylog-quality/run_graylog_quality.sh` — точка входа для cron.
- `/home/redos/graylog-quality/data` — отдельный `RT_DATA`; данные и расписание основного
  контейнера `rule-tester` не меняются.
- Graylog доступен по `http://127.0.0.1:9000`; используется рабочий `TB_GRAYLOG_TOKEN` из
  `/home/redos/ticketbridge/ticketbridge.env`. Старый `GRAYLOG_TOKEN` в `rule-tester.env`
  при первоначальной проверке вернул HTTP 401 и новым контуром не используется.
- IRIS читается через существующие `TB_IRIS_URL` и `TB_IRIS_KEY` из
  `/home/redos/ticketbridge/ticketbridge.env`. Значения секретов не выводятся и не копируются в отчёты.

## Что именно запускается

```bash
python3 rule_tester.py --url http://127.0.0.1:9000 --source live drift
python3 rule_tester.py --url http://127.0.0.1:9000 --source live \
  fp-check --since 7d --limit 2000
```

Код возврата `1` у этих команд означает наличие расхождений или совпадений, а не технический
сбой. Оркестратор продолжает работу и формирует отчёт. Коды `2` и отсутствие JSON-отчёта
помечаются как технические ошибки.

Перед проверками выполняется `git pull --ff-only`. Если обновить clone нельзя, задание
завершается с ошибкой, а не выдаёт проверку устаревшего каталога за актуальную.

## Учёт закрытых алертов IRIS

Выбираются записи со статусом `Closed` (`alert_status_id=6`) за 7 суток. Основное поле
времени — `resolved_at`. У старых записей оно может быть пустым; тогда используется
`date_update`, и число таких записей отдельно указывается в отчёте. Это время последнего
изменения, поэтому выборка может содержать алерты, закрытые раньше, но изменённые за период.

Timestamps IRIS без смещения интерпретируются как UTC и приводятся к локальной зоне сервера.
Разрешения не угадываются: пустое значение отображается как «Без разрешения».

### Кандидаты на тюнинг

В отдельную таблицу попадают только закрытия `False Positive` и `Legitimate`. Ответ списка
`/api/v2/alerts` уже содержит `alert_source_content`, поэтому оркестратор не запрашивает каждую
карточку отдельно. Из исходного события извлекаются только хост, пользователь и команда; сырые
события в сводку не копируются. Приоритет хоста — `host`, `wazuh_agent`, `agent_name`, `source`
и другие известные поля события; общий источник Graylog используется только как fallback.
Если агрегированный алерт не содержит поле, в отчёте явно пишется `(нет данных)`.

Группа содержит число закрытий, состав разрешений, последнее закрытие и до пяти ID примеров.
Повторяющиеся группы получают рекомендацию проверить запрос и добавить регрессионные
positive/negative-образцы. Единичные группы остаются на ручном разборе и наблюдении.
Ни одна рекомендация не создаёт исключение автоматически.

## Расписание и ручной запуск

Пользовательский cron `redos`, понедельник в **09:17 YEKT**:

```cron
17 9 * * 1 /home/redos/graylog-quality/run_graylog_quality.sh >> /home/redos/graylog-quality/data/cron.log 2>&1
```

Ручной полный запуск:

```bash
/home/redos/graylog-quality/run_graylog_quality.sh
```

Сокращённый технический прогон (24 часа, до 500 сообщений, итоги IRIS за сутки):

```bash
/home/redos/graylog-quality/run_graylog_quality.sh --since 24h --limit 500 --iris-days 1
```

Проверка сохранённого расписания:

```bash
crontab -l
```

## Файлы результатов

- `data/latest.md` и `data/latest.json` — последняя внутренняя сводка;
- `data/quality/YYYYMMDD-HHMMSS.md/json` — история внутренних сводок;
- `data/reports/` — исходные отчёты Rule Tester (JSON FP-check может содержать образцы логов,
  поэтому каталог остаётся только на сервере);
- `data/logs/` — технические журналы git/drift/fp-check;
- `data/cron.log` — журнал запусков по расписанию.

В Wiki и сводочный JSON попадают названия правил, счётчики, служебные поля, пути к отчётам,
а также хосты, пользователи и команды из кандидатов на тюнинг. Это внутренние данные лаборатории:
сгенерированные MD/JSON-отчёты и реальные значения таких полей нельзя коммитить в GitHub.
Сырые сообщения Graylog, описания алертов и токены в сводку не включаются.

## Границы проверки

- `fp-check` поддерживает числовые диапазоны Lucene, включая `[3 TO *]`. Для агрегаций оценивает
  `group_by`, скользящее окно `window_min`, простые пороги `count()` и составные `&&`/`||` с
  `count()` и `cardinality()`; точное расписание запуска Graylog не воспроизводится.
- Правила тишины и информационные сводки получают статус `НЕ ПРИМЕНИМО`: совпадения их запросов
  с отдельными сообщениями не считаются кандидатами на ложные срабатывания.
- Корпус ограничен 2000 последними сообщениями за окно и не является гарантированно «чистым».
  Совпадение может быть настоящей атакой; каждое нужно разбирать вручную.
- Нулевое число совпадений не доказывает отсутствие ложных срабатываний вне выборки.
- Повтор закрытия False Positive/Legitimate — только кандидат на разбор, а не доказательство
  ошибки правила. Нужно проверить исходный контекст и сохранить positive-контроль детекта.
- Аудит не исправляет правила, не закрывает алерты и не меняет скоринг TicketBridge.

## Регрессия фильтра штатных ответов Wazuh/IRIS

Для правила `WAZUH - Важный алерт (уровень 9-11)` в `rule-tester/samples/manual.json`
добавлены пять обезличенных образцов: четыре negative для штатных ответов 400/401 на API-точках
обновления сессии и фоновых запросов IRIS, один positive для ответа 401 на другом API-адресе.
Таким образом проверяются одновременно отсутствие известного шума и сохранение детекта.

```bash
python3 rule-tester/rule_tester.py --source file \
  --rule 'WAZUH - Важный алерт (уровень 9-11)' selftest
python3 -m unittest discover -s rule-tester -p 'test_*.py'
```

Проверка завершилась без технических ошибок на commit `75485ce`:

- каталог: 263 правила; Graylog: 267; расхождений: 39;
- FP-check: 263 правила, 247 без совпадений, 12 с совпадениями, 4 пропущены
  (тестер пока не поддерживает диапазоны `[a TO b]`); корпус — 2000 сообщений за 7 суток;
- IRIS: 1134 закрытых алерта за 7 суток — 943 False Positive, 141 без разрешения,
  30 Legitimate, 19 Unknown, 1 True Positive Without Impact;
- у 188 записей использован fallback `date_update`.

Эти числа — отправная точка для разбора, а не автоматическое заключение о качестве правил.
В частности, запросы правил тишины закономерно совпадают с отдельными сообщениями источника:
их нельзя оценивать как обычный детект по одному сообщению без учёта условия агрегации.

## Синхронизация первого отчёта (17.11.2026)

39 исходных расхождений разобраны вручную:

- **17 ожидаемых подстановок** — обезличенные `<белый список>`, `<IP>`, `<домен>`,
  а также три шаблона HEALTH и их развёрнутые экземпляры;
- **22 реальных отличия** — синхронизированы в обезличенный каталог из действующего Graylog:
  16 запросов, два ошибочно экспортированных составных условия и четыре отсутствующих
  определения Wazuh/Zabbix.

`drift` теперь сопоставляет placeholders по строгому шаблону: весь остальной запрос обязан
совпасть. Поэтому реальное изменение в другой части запроса не скрывается наличием белого
списка. Шаблон `<хост>` связывается с живым экземпляром только при однозначном совпадении.
Shell-перенаправления вида `< /dev/null >` placeholder не считаются.

Повторный серверный прогон: **267 правил в каталоге, 267 в Graylog, 0 расхождений,
17 ожидаемых подстановок**. Семь автоматических тестов сопоставителя пройдены. Действующие
определения Graylog при этой синхронизации не перезаписывались.

## Доработка FP-check (17.11.2026)

Добавлены числовые диапазоны Lucene и раздельная оценка событий, агрегаций, правил тишины и
информационных сводок. Для агрегаций одиночные совпадения больше не попадают в кандидаты без
выполнения условия внутри группы и скользящего окна. Поддерживаются составные `&&`/`||` с
`count()` и `cardinality()`. Статус `НЕ ПРИМЕНИМО` учитывается отдельно от технических пропусков
и не считается провалом в консольном отчёте, веб-интерфейсе и сводке HomeWiki.

Проверка доработки:

- 24 автоматических теста пройдено: диапазоны, границы, `*`, генерация образцов, пороги, группы,
  окна, составные условия, cardinality, тишина, сводки и JSON-сериализация;
- `selftest`: 267 правил, 1022 образца, нет правил без положительного образца и расхождений
  офлайн-вычислителя;
- финальный живой read-only FP-check за 7 суток, 2000 сообщений: 263 правила, 245 чистых,
  0 кандидатов, 18 неприменимых, 0 пропущенных запросов;
- сверка каталога: 267 правил здесь и в Graylog, drift 0, 17 ожидаемых подстановок.

Разбор прежних кандидатов не выявил инцидента: Linux — один успешный SSH-вход без порога 6 событий
и двух результатов `res`; Windows — два успешных Kerberos-входа `DC$` без ошибок 4625 и порога 5
событий; WireGuard — штатная ежедневная сводка. Правила Graylog не ослаблялись, исключения по хостам
не добавлялись: исправлена только оценка условий в FP-check.
