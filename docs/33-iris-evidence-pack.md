# Глава 33. IRIS: автоматический пакет доказательств для кейса

## Задача

При достижении порога корреляции TicketBridge создаёт кейс IRIS. Теперь вместе с ним формируется
снимок материалов расследования: исходные события Graylog, контекст хоста, активы, учётные записи,
IOC, комментарии, временная шкала и история обогащений. ZIP автоматически загружается в штатный
раздел **Evidences** кейса.

Ядро IRIS не изменяется: используются IRIS REST API, Datastore API и Graylog Search API.

## Архитектура

```text
Повторные события Graylog по связке «правило + актив»
  → TicketBridge: накопление скора и обогащение открытого алерта
  → достигнут TB_SCORE_THRESHOLD
  → штатная эскалация алерта в кейс IRIS
  → iris_evidence_pack.py: сбор снимка IRIS и Graylog
  → ZIP + manifest.json с SHA-256 содержимого
  → Datastore / Evidences, file_is_evidence=true
  → повторное чтение файла и сверка SHA-256
```

Пакет создаётся сразу после успешной эскалации — и при накоплении скора по нескольким событиям,
и при одиночном правиле, чей вес сразу достигает порога. Сам кейс не зависит от успеха упаковки:
если сбор или загрузка ZIP завершились ошибкой, уже созданный кейс сохраняется, а TicketBridge
отправляет в Graylog `tb_event=iris_evidence_pack_error`.

## Что входит в ZIP

| Путь | Содержимое |
|---|---|
| `README.md` | краткая сводка: кейс, алерт, скор, активы, число событий и ссылки |
| `iris/case.json` | карточка кейса |
| `iris/alerts.json` | связанные алерты |
| `iris/alert_comments.json` | комментарии по каждому алерту, включая историю обогащений в комментариях |
| `iris/assets.json` | активы кейса и каждого алерта: хосты и учётные записи |
| `iris/iocs.json` | IOC кейса и алертов |
| `iris/timeline.json` | события и временная шкала кейса |
| `iris/notes.json` | заметки |
| `iris/enrichment_history.json` | история изменений алертов |
| `iris/previous_evidences.json` | реестр доказательств, существовавших до загрузки |
| `graylog/trigger_event.json` | событие, вызвавшее эскалацию |
| `graylog/original_events.json` | исходные сообщения по `replay_info` |
| `graylog/context_events.json` | сообщения главного хоста за то же replay-окно |
| `graylog/replay.json` | запрос, интервал и потоки исходного replay |
| `links.json` | ссылка на Graylog Replay Search и найденные ссылки TrafficLens |
| `collection_errors.json` | ошибки отдельных необязательных источников |
| `manifest.json` | размер и SHA-256 каждого перечисленного файла |

Для исходных сообщений используются запрос, временные границы и потоки из `replay_info`. Контекст
главного хоста ищется отдельно **по всем потокам**: события Wazuh, osquery или Sysmon могут не
входить в поток правила, которое вызвало кейс. Каждый из двух поисков ограничен
`TB_EVIDENCE_RAW_LIMIT` сообщениями.

Ссылки TrafficLens добавляются только тогда, когда URL действительно присутствует в событии.
Отсутствующий PCAP или отчёт не выдумывается. Сетевые адреса, порты, процессы и командные строки
сохраняются в выгрузках Graylog, если они есть в исходных полях.

## Целостность и загрузка

Перед созданием ZIP вычисляются размер и SHA-256 каждого содержимого файла; эти сведения пишутся
в `manifest.json`. Для самого ZIP отдельно вычисляется внешний SHA-256.

Модуль находит штатную папку `Evidences` через дерево Datastore и отправляет multipart-запрос с
`file_is_evidence=true`. После загрузки он:

1. повторно читает информацию о файле;
2. сравнивает SHA-256, записанный IRIS, с хешем локального ZIP;
3. проверяет появление записи в `/api/v2/cases/{id}/evidences`.

При несовпадении хеша или отсутствии записи операция считается ошибкой, а не успешной загрузкой.

## Настройки

| Переменная в `ticketbridge.env` | Умолчание | Назначение |
|---|---:|---|
| `TB_EVIDENCE_PACK` | `1` | автоматически прикладывать ZIP при эскалации; `0` отключает только пакет |
| `TB_EVIDENCE_RAW_LIMIT` | `200` | максимум сообщений в каждом Graylog-поиске пакета |

URL и ключи IRIS/Graylog берутся из существующих `TB_IRIS_URL`, `TB_IRIS_KEY`, `TB_GRAYLOG_URL` и
`TB_GRAYLOG_TOKEN`. Секреты в архив отдельно не записываются.

После изменения настроек:

```bash
systemctl --user restart ticketbridge
systemctl --user is-active ticketbridge
curl -fsS http://127.0.0.1:8099/health
```

## Ручной запуск для существующего кейса

На `redos-server`:

```bash
set -a
. /home/redos/ticketbridge/ticketbridge.env
set +a
python3 /home/redos/ticketbridge/iris_evidence_pack.py CASE_ID --alert-id ALERT_ID
```

`--alert-id` нужен, чтобы однозначно выбрать главный алерт, его replay-окно и активы. Результат —
JSON с `file_id`, `evidence_id`, именем ZIP, размером, SHA-256 и количеством собранных сообщений.
Повторный запуск создаёт новый снимок с новой меткой времени; прежние доказательства не удаляются.

## Частичные ошибки и ограничения

- Недоступность комментариев, активов, IOC, заметок или контекстного поиска фиксируется в
  `collection_errors.json`; остальные доступные материалы сохраняются.
- Ошибка чтения самого кейса/алертов, загрузки или проверки хеша прерывает создание пакета.
- Ошибка пакета не откатывает кейс и не меняет исходный алерт.
- Это **снимок на момент формирования**, а не живой синхронизированный архив: последующие
  комментарии, активы и изменения кейса в старый ZIP не попадают.
- Если старые сообщения уже вышли из срока хранения индексов Graylog, восстановить их пакет не может.

## Наблюдаемость и тесты

В Graylog пишутся:

- `tb_event=iris_evidence_pack` — успешная загрузка, с ID кейса, алерта, файла и evidence;
- `tb_event=iris_evidence_pack_error` — кейс создан, но пакет не приложен;
- прежнее `tb_event=iris_escalated` — сама эскалация.

Проверки `ticketbridge-corr/test_evidence_pack.py` покрывают состав ZIP и manifest, поиск контекста
по всем потокам, загрузку в Evidences с проверкой хеша, успешную интеграцию и сохранение кейса при
ошибке пакета. Совместный прогон с тестами типизации активов: **8 passed**; `py_compile` успешен.

## Живая проверка 17.11.2026

Пакет вручную сформирован для существующего кейса IRIS №25, связанного с алертом №1172:

- файл `case-25-evidence-20261117T155229Z.zip`;
- `file_id=1`, `evidence_id=1`;
- размер 15 892 байта;
- SHA-256 `24cf426b9739cb17c7483563350fc7f5b1fa4ddbb6773739fdfc904560b6e5b2`;
- 7 исходных и 152 контекстных сообщения Graylog;
- 0 ошибок сбора.

ZIP затем скачан обратно через Datastore API: внешний SHA-256 совпал, структура ZIP прошла проверку,
все 16 записей manifest совпали по размеру и SHA-256. Всего архив содержит 17 файлов, включая сам
manifest. После установки в production TicketBridge перезапущен, находится в `active`, `/health`
возвращает успех, ошибок в журнале запуска нет.

Автоматический вызов дополнительно проверен unit-тестами. Искусственная эскалация ради повторного
живого теста не создавалась.
