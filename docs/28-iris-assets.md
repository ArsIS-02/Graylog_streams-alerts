# Глава 20. IRIS: обогащение алертов активами

> Каждый алерт, приходящий из Graylog в DFIR-IRIS, автоматически получает список затронутых
> активов: хосты (с типом по ОС и IP), учётные записи, неизвестные адреса как IOC.
> Активы из алертов складываются в реестр **Manage → Assets** — получается самообновляемый CMDB.

## Зачем

Алерт без контекста — это строка текста. Алерт с активами отвечает на вопросы «на каком хосте»,
«какая учётная запись», «какие адреса участвуют» — и позволяет IRIS связывать похожие алерты
(similarity по общим активам) и считать sightings актива по всей истории инцидентов.

## Архитектура

```
Graylog (event definition срабатывает)
  └─ HTTP-уведомление → TicketBridge (:8099/hook, systemd user service)
       ├─ collect_observables(event) — извлечение активов и IOC (3 уровня, см. ниже)
  └─ POST /api/v2/alerts в IRIS (поля alert_assets, alert_iocs)
       ├─ активы алерта: case_assets + alert_assets_association
       └─ sightings → реестр Manage → Assets (managed_asset, source=observed)
```

Источники инвентаря:

| Источник | Что даёт | Как читается |
|---|---|---|
| **HostDeck** | хосты с агентами (имя, ОС, профиль, IP) + ручные метки `net_labels` для устройств без агента (роутер, принтеры, DC, VPN-адреса) | `GET /api/export/hosts.csv?key=ip\|name&header=0`, кеш 5 минут |
| **Graylog API** | исходные сообщения события (хост-источник, IP, учётки) | legacy-поиск `/api/search/universal/absolute` по `replay_info` события; токен с правом чтения поиска |

## Три уровня извлечения активов

`collect_observables(event)` в `ticketbridge/app.py`:

1. **Структурированные поля события** — `srcip`, `dstip`, `agent_ip`, `source`, `hostname`,
   `user`, `acct`, `username` и т.п. Самый чистый источник, но Graylog заполняет его,
   только если поля явно настроены в event definition.
2. **Текст сообщения** (`fields.event` + `message`) — regex по IPv4, поиск имён хостов из
   HostDeck с границами слов (имена короче 5 символов и общеупотребительные слова пропускаются,
   чтобы не ловить ложные совпадения), учётные записи по шаблонам `acct=`/`user=`/`username=`.
3. **Graylog replay** — если первые два уровня пусты, из `replay_info` события берутся запрос,
   таймрейм и стримы, и выполняется поиск до 5 исходных сообщений. Из них извлекаются
   `source` (хост-источник лога), `gl2_remote_ip`, поля пользователей.

Правила типизации:

| Что нашли | Становится |
|---|---|
| IP/имя, известное HostDeck | актив с типом по ОС (Linux Server/Computer, Mac, Windows, Windows DC, Router) |
| Неизвестный IP | IOC `ip-any` |
| Учётка `DOMAIN\user` или машинная `PC$` | актив «Windows Account - AD» |
| Прочая учётка | актив «Account» |

Лимиты: до 10 активов и 10 IOC на алерт.

## Грабли, которые мы уже прошли

- **`event.source` — это Graylog-сервер, а не жертва.** У события Graylog поле `source`
  содержит имя узла Graylog (`home.apps...`). Хост-источник события надо брать из текста
  сообщения или из исходных логов через replay. Именно из-за этого обогащение когда-то
  молча ничего не находило: 0 из 100 алертов имели активы.
- **Legacy-поиск Graylog требует параметр `fields`**, иначе HTTP 400.
- **Заголовок алерта — тоже источник.** Многие правила (например, honeytoken-ловушки)
  несут имя хоста только в заголовке. При бэкфилле добавляйте `alert_title` в разбираемый текст.
- **REST API алертов не умеет обновлять активы** — обновление существующих алертов делается
  прямыми вставками в Postgres (`case_assets` + `alert_assets_association`), одной транзакцией.
- **Observed-записи реестра приходят голыми.** IRIS создаёт их из активов алертов
  автоматически, без IP/домена — дополняйте через `PUT /api/v2/manage/managed-assets/{id}`.
  Числовые «учётки» вида `1000` (UID из audit-логов) удаляйте.

## Бэкфилл исторических алертов

Два прохода по закрытым алертам без активов:

1. **Текстовый** (быстрый, без запросов к Graylog): событие + заголовок → `collect_observables`.
2. **Replay** (по одному поисковому запросу на алерт): для тех, где текст пуст, — выборка
   исходных сообщений через `replay_info`.

Результат на нашей лаборатории (~1100 закрытых алертов): покрытие активами выросло
с 21% до 78%. Остальное — события, чьи сообщения уже вышли из ретеншена индексов.

## Эксплуатация

- Новый хост без агента HostDeck (роутер, IoT, чужая железка) → добавьте метку в `net_labels`
  HostDeck, иначе его адреса будут попадать в IOC вместо активов.
- Токены и URL хранятся в `ticketbridge.env` (права 600, вне репозитория).
- Реестр активов входит в ежедневный бэкап IRIS (дамп Postgres).

## Чистка реестра (16.11.2026)

Ревизия реестра после двух дней эксплуатации:

- **IP-адреса приведены к HostDeck** (269 записей `case_assets`): redos-raspi .106→**.149**
  (адрес сменился 15.11), проставлены homelab **.210**, homeserver **.56**, redosrp16 **.55**,
  server.monitoring.test **.50**, MacBookPro-M4Pro **.5**.
- **`gl2_remote_ip` в Graylog не годится для различения хостов** за ретранслятором:
  server.monitoring.test (.50) и wazuh-homelab.monitoring.test (.37) присылают логи
  через redosrp16 (.55), поэтому у обоих `gl2_remote_ip=.55`. Источник истины по
  адресам — агентский инвентарь HostDeck.
- **Мусорные «учётки» удалены** (7 шт., транзакцией — сначала `alert_assets_association`,
  потом `case_assets`): `1000`, `dfir-iris.service`, `homewiki-backup.timer`,
  `iris-backup.timer`, `soc-watchdog.timer`, `zabbix-analytics.timer`.
- **Парсер дополнен фильтром `_is_valid_user`**: не берёт в активы суффиксы
  `.service/.timer/.socket/.mount/.target/.scope`, числовые UID и системные имена
  (unknown/system/local/network) — мусор больше не регенерируется.
